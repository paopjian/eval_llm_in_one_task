## 失败原因分析

### GLM-Pro 系统内存爆满
```
初始GPU状态：
- 7卡利用率：99-100%
- 显存占用：7.7GB/卡（正常）

系统内存增长：
- 初始：10GB
- 30秒后：28GB (+18GB)
- 60秒后：158GB (+130GB，持续暴增）

问题：代码设计缺陷，计算过程中系统内存持续增长
结论：非参数问题，是代码实现问题
```

### DeepSeek-Pro 系统内存爆满
```
初始GPU状态：
- 7卡利用率：99-100%
- 显存占用：7.7GB/卡（正常）

系统内存增长：
- 初始：10GB
- 30秒后：28GB (+18GB)
- 60秒后：158GB (+130GB，持续暴增）

问题：与GLM-Pro相同的内存泄漏问题
结论：代码设计缺陷，无法完成200万数据评估
```

### Codex-Sol-M 并行失败
```
GPU状态：
- 7个GPU进程都启动，各占8GB显存
- 但只有1个进程在工作（CPU 100%）
- 其余6个进程处于等待状态
- GPU利用率0-9%

问题：multiprocessing的spawn模式在7卡并行时有问题
结论：代码实现缺陷，codex-sol和codex-sol-2都成功了
```

## 结论

### 成功的模型特点
1. **合理的显存管理**: 成功的模型都有良好的GPU显存分配策略
2. **高效的并行计算**: Codex-Sol-2和Gemini展现了优秀的多GPU并行能力
3. **优化的算法**: GLM仅用47秒完成200万数据评估，算法高度优化
4. **稳定的内存使用**: 系统内存占用稳定，无泄漏问题

### 失败的模型问题
1. **系统内存泄漏**: GLM-Pro和DeepSeek-Pro都存在严重的内存泄漏，系统内存在1分钟内从10GB暴增到158GB
2. **并行实现缺陷**: Codex-Sol-M的multiprocessing实现有问题，7个GPU只有1个在工作
3. **代码设计缺陷**: 这些失败都不是参数调优能解决的，是代码实现层面的问题

### 最终统计
- ✅ **成功**: 6个模型 (qwen, glm, gemini, grok, codex-sol, codex-sol-2)
- ❌ **失败**: 3个模型 (glm-pro, deepseek-pro, codex-sol-m) - 都是代码实现问题
- ⚠️ **未测试**: 2个模型 (claude-opus, deepseek) - 需修改硬编码路径

### 建议
1. **GLM-Pro和DeepSeek-Pro**: 需要重写内存管理逻辑，修复内存泄漏问题
2. **Codex-Sol-M**: 需要修复multiprocessing并行实现
3. **Claude-Opus和DeepSeek**: 需要修改脚本支持自定义数据路径参数
4. **最佳模型选择**: 
   - 追求速度: GLM (47秒) ⚡
   - 追求稳定: Codex-Sol-2 (52秒，负载均衡好)
   - 追求吞吐: Gemini (37.758 Giga-Pairs/s)
