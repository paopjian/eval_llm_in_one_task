## 📈 性能分析

### 1. 为什么hybrid_optimal最快？

**技术组合**:
```
ThreadPoolExecutor (省27秒启动)
+ TF32精度 (核心计算快5倍)
+ 对数切分负载均衡 (88%均衡度)
+ 200K bins (高精度)
= 0.348秒总耗时 ⚡⚡⚡
```

**与grok对比**:
- grok使用FP32，核心计算0.851秒
- hybrid使用TF32，核心计算0.170秒
- **TF32加速: 5.0×**

### 2. 为什么Spawn方法这么慢？

**时间分解** (以codex_tf32为例):
```
总耗时: 27.472秒
├─ 数据加载: 0.615秒 (2.2%)
├─ 核心计算: 0.448秒 (1.6%)
└─ 进程启动: 27.024秒 (96.2%) ← 瓶颈！
```

**Spawn启动开销包括**:
- 7个独立进程启动
- 每个进程的CUDA初始化
- 数据序列化和传输
- 进程间通信建立

### 3. TF32 vs FP32精度对比

**核心计算时间**:
- hybrid_optimal (TF32, 200K bins): 0.170秒
- codex_tf32 (TF32, 200K bins, Spawn): 0.448秒
- grok_threadpool (FP32, 100K bins): 0.851秒
- deepseek_precise (FP32, 200K bins): 0.444秒

**TF32优势**:
- 在ThreadPool模式下: 5.0× 加速（0.170秒 vs 0.851秒）
- 在Spawn模式下: 与FP32相当（被启动开销掩盖）

**精度对比** (TPIR@FPIR=1e-5):
- 所有方法: 63.95-63.96%
- **精度差异: <0.01%** (可忽略)

### 4. Bins数量影响

| Method | Bins | 核心计算 | 影响 |
|--------|------|---------|------|
| grok | 100K | 0.851秒 | 基准 |
| codex/deepseek | 200K | 0.444-0.448秒 | 相当 |
| glm | 2M | 0.477秒 | 轻微增加 |

**结论**: Bins从100K→2M，性能影响<12%

## 💡 关键洞察

### 1. 架构选择决定性能上限 ⚡⚡⚡

**线程池 vs Spawn性能对比**:
```
相同算法，不同架构:
- ThreadPool: 0.348-1.019秒
- Spawn: 27.472-28.342秒
差距: 79-81倍
```

**原因**: Spawn启动开销占98%时间

### 2. TF32显著加速核心计算

**ThreadPool模式下**:
- hybrid (TF32): 0.170秒
- grok (FP32): 0.851秒
- **加速: 5.0×**

**精度损失**: 可忽略(<0.01%)

### 3. 负载均衡策略影响有限

| 策略 | 均衡度 | 代表 |
|------|-------|------|
| 对数切分 | 88-94% | hybrid, grok |
| 贪心分配 | 79-82% | codex, glm |
| 轮询分配 | 85% | deepseek |

**结论**: 在Spawn模式下，负载均衡优化被启动开销掩盖

### 4. Bins数量影响不大

100K → 2M bins，性能变化<12%

### 5. 开发效率差异明显

- 最快: gemini场景 8.7分钟
- 较快: deepseek 26.4分钟, codex-sol 29.5分钟
- 较慢: codex-sol-2 77.3分钟
- 最慢: claude-opus 231.3分钟（但有完整迭代记录）
