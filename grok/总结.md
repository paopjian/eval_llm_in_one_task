## 2. 关于「只用了 1.3s」——是的，但要分清是哪一段

**1.31s 是 7 卡上三角相似度直方图这一段，不是从打开 Python 到退出，更不是整个 LLM 写代码会话。**

最终一次完整运行（`python eval_similarity.py`）的脚本内计时：

| 阶段 | 耗时 | 含义 |
|------|------|------|
| 读 pkl | 0.32s | 加载特征 / 标签 / 路径 |
| 正样本对 | 0.82s | 按身份 batched GEMM，2,179,084 对精确分数 |
| **多卡直方图** | **1.31s** | **20,651,927,761 对上三角相似度统计** |
| 样本对提取 + 写 TSV | 0.32s | 阈值 0.3133 下的 FP/FN/TP |
| **脚本业务合计** | **2.78s** | 以上四项之和 |
| 进程墙钟（含 import/CUDA 初始化） | ~9.3s | 工具记录的进程 Duration |

速度：`20,651,927,761 / 1.31s ≈ 15.7 G pairs/s`。

### 为什么 1.3s 合理，不是计时错误

计算量（上三角点积）：

```
20.651927761e9 pairs × 512 × 2 FLOP ≈ 21.15 TFLOP
```

7 × RTX 4090 的 FP32 峰值大约 7 × 82.6 ≈ 578 TFLOPS，纯 GEMM 理论下限约 **0.037s**。  
实测 1.31s 对应有效算力约 16 TFLOPS（峰值的 ~3%），瓶颈在 `histc`、分块 kernel、写出/读回相似度，而不是矩阵乘本身。量级上完全站得住。

对比实验也支持这个数字：

- 多进程 `spawn` 版直方图墙钟 **4.38s**（7 个进程各自 import torch + 拷特征，启动开销大）
- 同进程 `ThreadPoolExecutor` 版 **1.31s**（CUDA 上下文已在，拷到 7 卡后并行 GEMM+histc）
- 单卡 worker 自己报的 kernel 时间本来就是 0.8–1.3s；7 卡负载按对数均分，墙钟被最慢那张卡卡住，所以总直方图就是 ~1.3s

**结论：1.3s 是 206 亿对多卡统计的真实耗时；端到端拿到图和 TSV 大约 3s（不含 Python 启动），整个 LLM 迭代写代码另计，见下一节。**

## 6. 实现要点（和速度的关系）

1. **不物化 NxN 矩阵**：206 亿对 float32 要 82.6GB，7 卡分块 GEMM 后立刻 `histc` 进 10 万 bin。
2. **正样本单独算**：每人最多 38 张，batched `bmm` 即可，2.18 万对精确分数用来算 TPIR。
3. **负样本用直方图**：FPIR 阈值从「全体上三角直方图 − 正样本」反推；正样本改用同一套 `torch.histc` 后，负样本计数与解析解一致。
4. **7 卡按上三角对数切行**：每卡约 14.29% 的对数，避免「前几行对很多、后几行对很少」的闲置。
5. **线程而不是 spawn**：省掉 7 次进程启动和重复 import，直方图从 4.38s 降到 1.31s。
6. **提取不二次全扫**：第一遍同时保留每卡 top-100k 高分负对，阈值出来后直接筛 FP。
